# Modular Elden Ring–style combat for RustWrath

**Superseded (2026-11-14)** — the server-authoritative admission/receipt model here is replaced
by the client-authority redesign in [souls-combat-client-authority.md](souls-combat-client-authority.md).
Kept for its hit-integration and animation research; do not implement the wire design.

**Status** — Proposed implementation plan, 2026-11-13. Source baseline is RustWrath `main` at `38f56810`, matching remote `main` at initial inspection. Implementation follows owner acceptance of the Northshire alpha route, as recorded in [owner decisions](../baseline/owner-decisions.md). Start with an opt-in private PvE encounter and expand through weapon, enemy and spell profiles. First authored content targets one human rig, a sword and shield, a humanoid melee enemy and a caster.

## What the player should be able to do

Walk into an encounter with a melee enemy that closes distance, visibly winds up, commits its swing, and leaves an opening. Dodge through the strike or step outside its reach, then punish with a light attack. A shield offers a slower defensive option with a stamina cost. A heavy attack buys more stagger at the cost of commitment. A caster changes the spacing problem with a readable projectile. The player can equip a learned spell as an action and cast it through that same windup, interrupt and recovery system. These are successive milestones. The stationary dodge is an integration probe on the way to that loop.

## Ownership and interfaces

| Owner | State it writes and interface it exposes |
| --- | --- |
| AzerothCore world/map update | Effective combat mode, stamina, phase, action instance, authoritative tick, and allowed hit windows. It consumes `ModeRequest` and `ActionIntent`, and emits `ModeState`, `ActionReceipt`, and a bounded `CombatSnapshot`. Existing AzerothCore paths own HP, absorbs, procs, death, loot, XP and quest credit. |
| `benilla-combat-core` | Rules for ordered gestures, buffer, action phase, stamina and eligibility. Extract that reusable rules surface from the fixture. The live caller advances the rules and queries dodge eligibility at its hit seam. Keep fixture enemy damage and HP mutation in the offline harness. |
| `benilla-app` combat host | Input ownership, world-session generation, sequence allocation, bounded send/receipt tracking, predicted state and replica. It applies the server snapshot and projects the result to movement, pose, targeting and UI. A locally timed-out receipt clears the pending prediction. A newer valid snapshot can still converge state without replaying the action. |
| `CombatModuleV1` client DLL | A replaceable mapping from a bounded host snapshot and ordered input edges to action proposals and presentation cues. Use stable action IDs, integer ticks, bounded POD data and host-owned memory. Host validates outputs and owns all state needed to replace the DLL. Raw spell IDs, hit targets and authority flags from the staged descriptor should be removed or kept entirely outside the commit path. If an existing binary consumer is found, version the revised descriptor and entry point. |
| Movement, pose, camera and UI | Movement consumes a bounded intent and commits collision-checked movement. Pose and animation select clips using action ID and phase. Camera uses existing target/lock ownership. UI shows server stamina and mode, with prediction visibly distinguishable where needed. Combat log and hit reactions consume server outcomes. |
| WM and authored data | WM can publish an immutable validated `ActionRevision` and observe combat. The authoritative map update consumes an admitted revision locally. It owns action timing and eligibility during the encounter and stays off the DB/SOAP and Python request paths for each hit. |

For a shared live rules implementation, first prove a narrow Rust/C ABI can link into the existing Windows AzerothCore build. Use opaque state handles and fixed-layout values at that seam. If the toolchain rules out that route, choose a server-native implementation only after defining conformance vectors for gesture thresholds, tick order, stamina and boundary cases. Keep the client’s predictive copy disposable.

### Wire and tick order

1. In explicit experimental opt-in, negotiate the wire version, supported actions and `ActionRevision` over the authenticated world session. Evaluate the existing addon-message path as the first carrier candidate. Prove both receiver directions and scope binding before selecting it. Ordinary Baseline sessions send zero extension traffic. The server’s `ModeState` activates Experimental only when the character and encounter are eligible and the previous attack/cast ownership has settled. Server-side gates prevent auto-attacks and direct casts from bypassing the experimental action rules. Actions explicitly routed through the existing spell engine still use its cast and effect checks.
2. Capture press/release and intended movement direction in sequence order. The host sends session/encounter generation, sequence, revision and action input. The server binds the actor to the authenticated session, assigns the tick from its own clock and checks eligibility and scope. Inputs on the same tick retain order. A delayed input cannot change a strike that already resolved.
3. At the map update seam, end expired actions, apply ordered input and the buffer, commit legal movement, then resolve active strikes against that tick’s authoritative world state. Publish receipts with sequence, action instance, start tick and accepted/refused reason. Publish snapshots with revision, tick, phase, stamina and accepted sequence. Retire scopes on death, transfer, logout, disconnect and mode exit. Reject stale generations, revisions and duplicate inputs before applying side effects.
4. On the client, drain network updates before prediction, then submit validated movement intent before controller integration. Drive animation from the predicted/accepted action clock and reconcile on receipt. Preserve standard Wrath outcomes for damage and rewards. Log sequence, action instance, revision, server tick and outcome together so a roll can be traced from input to actual hit resolution.

### Hit integration and movement

- Start with one allowlisted NPC strike and a stationary dodge to prove the authority seam. In the inspected AzerothCore source at `5e741c3`, `Unit::CalculateMeleeDamage` chooses the melee outcome before its outcome switch and absorb calculation. Investigate selecting deterministic `MELEE_HIT_DODGE` at outcome construction, with explicit standing/eligible actor checks and the stock packet/proc path. The current `OnBeforeRollMeleeOutcomeAgainst` changes chance inputs, and the subsequent roll and sitting-victim override can still determine the result. If the installed module API cannot express the required result, document the gap and design a narrow deterministic outcome hook for a planned maintenance deployment. Keep periodic, environmental, secondary, PvP and ordinary Wrath attacks on their stock paths. See the [existing server integration map](../opencode/combat-core-integration.md#9-server-hit-outcome-call-graph-read-only-source-map).
- Add moving rolls only once the server can validate direction and displacement against existing map collision, locomotion constraints and movement ownership. The client controller predicts the same bounded motion and accepts server correction. Animation and pose follow committed movement. A clip’s root motion cannot move the world entity on its own.
- Add one light attack through a server-owned action ID. For the first hit shape, use server range, facing and line-of-sight at the active tick, with at most one outcome per action instance and target. Route a successful strike through an explicitly reviewed AzerothCore damage path. Introduce swept weapon volumes only when server geometry and replication are ready to support them.

## Animation production and integration

**Yes, author new animations.** Use existing WoW clips and visual kits to get the network and combat paths working, then replace the motions that communicate commitment and timing. The first authored pack should include a directional dodge roll, a light sword slash, a heavy windup and strike, a shield raise/hold/release, a stagger, and the melee enemy’s normal and delayed swing. Start the roll with a forward clip rotated by the movement controller in free aim. Add dedicated back and side clips for lock-on once the basic blend is reliable. For the first spell, reuse its Wrath cast and impact kit with the new action timing. Author a distinct charge pose and release clip when charged spells enter the move set.

1. **Rig and export.** Pick one exact M2 skeleton/profile for the player and one for the enemy. Create a local animation-authoring rig from the skeleton hierarchy, pivots and reference pose. Animate in Blender, bake transforms and try glTF as the offline interchange format for the first full-body roll. Use the conversion spike to produce the `AnimationClip` and `PoseClip` pair already produced by [`build_animation_clip`](../../crates/benilla-assets/src/model.rs#L433). Establish axis, unit, bind-pose and bone-mapping rules against that actual model. Store original clips, rig maps and markers as versioned content. Keep extracted M2 models and third-party game assets local. Check weapon attachment and hand grip through the conversion.
2. **Play clips through the existing animation owner.** `benilla-assets` already reads M2 skeletons and embedded/external animation sequences. Extend the [`creature_anim` driver](../../crates/benilla-app/src/creature_anim/driver.rs) with an action-instance request that resolves an authored clip or a per-rig M2 fallback, then uses the existing [`RigPose`](../../crates/benilla-world/src/rig_anim/pose.rs) pipeline. Dodge and committed swings claim the full body. A guard hold or an eligible cast can use an upper-body layer with locomotion below it. Death and forced control override an action, and matching interrupt/end events release its claim and blend back to locomotion. Keep pose hotpatching in its existing post-evaluation position.
3. **Line up motion, effects and hits.** Each clip carries contact, release, foot-plant and audiovisual markers. Validate contact/release against the authored action’s active ticks during content staging. On the wire, replicate actor, action instance, revision, start tick and facing so observers can play the correct segment after a late packet. Play windup and trails from the action timeline. Trigger hit reactions, impact sound and damage text from the server’s outcome, deduplicated against existing Wrath animation and spell events. A rendered contact marker cannot cause a hit. Extract the desired roll displacement as a separately authored movement curve and keep the skeletal clip in place. The controller and server cap or stop travel at collision.
4. **Admit new rigs deliberately.** Each rig profile needs compatible bone mappings, attachments, motion scale and a readable fallback for its assigned actions. Use an explicit roster for the first release. Verify the actual base/HD profiles used by the encounter before enabling them. A missing critical telegraph or incompatible rig keeps that actor/profile out of the encounter until a usable fallback is staged. Retarget to a second race and a different NPC rig before claiming reusable production support.

Source anchors are the [M2 asset loader](../../crates/benilla-assets/src/m2.rs), [animation selection](../../crates/benilla-app/src/creature_anim/select.rs) and [spell visual router](../../crates/benilla-app/src/creature_anim/spell_visual.rs). New work includes the clip import path, action-instance playback and revision-aware visual ownership.

## Enemy conversion

Use a server-owned enemy profile selected for an opted-in encounter and bound to its spawn or creature template. AzerothCore `SmartAI::UpdateAI` currently advances scripts and can call `DoMeleeAttackIfReady`; the source also exposes chase, cast, auto-attack and combat-movement controls. Use those for a narrow prototype where they fit. For the playable encounter, prefer a dedicated `CreatureAI` adapter if SmartAI cannot express an atomic telegraph → commit → strike transition. One decision owner runs per converted enemy. The adapter uses existing threat, navmesh/chase, leash, evade, death and loot owners and disables stock swing/cast scheduling for that spawn during its experimental fight.

| Profile | Behavior and tuning |
| --- | --- |
| Sword enemy | Approach with `MoveChase`, stop in attack range and pick a fast swing or delayed overhead using distance and an authored cooldown/weight. Limit rotation during windup, commit direction at the authored point, and test range, facing and line of sight at contact. Whiff when the player exits reach. Expose a recovery punish window and reset cleanly on evade. |
| Shield enemy | Guard from the front, drop guard on a committed attack, and expose its side/back. Tune guard stamina or posture, guard-break threshold, punish duration and the time before it can raise guard again. Add once light/heavy/guard outcomes are proven. |
| Caster | Seek a preferred range and line of sight, telegraph one projectile, and use the same action clock for release, interruption and recovery. Resolve projectile impact with server position and eligibility. Reposition when the target closes or breaks line of sight. |

The AI chooses actions and navigation goals. The combat rules own their windows, and movement commits positions. Replicate telegraph start and interruption to all eligible observers. Cancel scheduled actions on death, leash/evade, invalid target, transfer or encounter teardown. Restrict the first encounter to its admitted participants and reset the fight if the player leaves its bounds. When groups enter scope, add a per-encounter budget for simultaneous attack starts so windups can overlap intentionally and recovery stays readable. Convert enemies by encounter first, then by archetype. Existing creatures outside those assignments continue to use their current profiles and AI.

## Player input, weapons, skills and spells

Give Experimental mode its own rebindable controls and action slots. The proposed starting layout is light, heavy/hold to charge, dodge, guard, lock-on and a small set of equipped spell/skill slots. In free aim, facing/direction is sampled from current movement and camera input. Lock-on supplies a target hint and orients the player through the existing camera and movement owners. The server validates facing and target eligibility independently. The weapon profile selects its compatible moves, reach, combo follow-ups and guard options from equipped gear. Changing a weapon or loadout in an encounter is restricted to an agreed neutral state. The active action keeps the loadout and revision admitted at its start.

| Input | Experimental action and resulting server operation |
| --- | --- |
| Light / heavy / charge | Resolve a stable action ID from the current weapon profile. The server spends stamina on acceptance, advances windup, selects the validated hit at contact, and allows a follow-up only in the authored cancel window. Charge uses ordered press/release, a server-bounded hold time and an explicit early-release behavior. |
| Dodge / guard / parry | Route through the same action state. Dodge publishes its accepted i-frame window. Guard evaluates angle and stamina at contact and can break on depletion. Parry requires an allowlisted incoming action and opens a server-owned riposte opportunity. Start with dodge, then guard, then parry. |
| Equipped class spell | Start with one direct projectile from the character’s learned spells. The server resolves the pinned action binding, checks learned spell, equipment/form, target, costs and cooldown, then invokes the existing spell engine at release. The action owns windup and recovery. Select an instant or explicitly adapted effect spell so the ordinary cast time does not add a second windup. Preserve the actual spell pipeline for damage, power, cooldown, threat, auras and logs. |
| Weapon skill / Spellwright spell | Resolve a stable action ID to an allowlisted existing spell or an immutable purchased Spellwright spell ID. Keep graph effects in their existing owners and action timing in the combat profile. Spellwright purchase and graph lifecycle remain on the existing path. A live action-to-spell binding and its rollback need implementation. |
| Unsupported spells, items, macros and direct cast input | In the initial encounter, allow only explicitly mapped combat actions. Apply the same server admission to action slots, direct `CastSpell` calls, macros, auto-repeat, item uses and pet commands that could bypass commitment. Show a typed refusal for a blocked action. Route permitted noncombat or explicitly adapted uses to their existing owners. |

Keep stock spellbook, equipment and spec state as the source for eligibility. The experimental slots store bindings to logical actions and learned abilities. They do not rewrite the 144 stock slots. Entering or leaving the mode switches the active input routing and UI projection. A spec/equipment change invalidates incompatible bindings and the server checks them again. At the client’s existing [`use_action`](../../crates/benilla-app/src/ui_action/drain.rs) and [cast ingress](../../crates/benilla-app/src/spell/cast_send.rs), route opted-in intents to the experimental action owner. Enforce the same policy server-side for stock `HandleCastSpellOpcode`, auto-attack and other admitted entry points.

For the projectile pilot, stamina and spell power have separate owners. Weapon actions spend stamina at acceptance. The spell engine charges power/reagents and sets spell cooldown once when it accepts the release. Reserve the action through windup, revalidate at release, and publish the failure or interrupt with its action instance. An interrupted windup produces no spell effect. Reuse the cast/impact feed for real spell outcomes and suppress duplicate presentation keyed to the same instance. Explicitly specify per-spell target policy, movement permission, cancellation, cooldown/GCD interaction and delivery type. Add ground targeting, channels, heals, interrupts, procs and periodic effects one family at a time. Each needs a release and interruption policy before it can enter the experimental loadout. See the [existing cast/action trace](release-matrix-2026-11-05.md) and [Spellwright publication contract](../live-rules/B-001B-1-contract.md).

## Content definitions and live tuning

Publish compatible action, weapon, enemy and animation profiles under one immutable revision. The server validates action IDs, phase ticks, buffer/cancel windows, stamina and poise costs, target constraints, hit shape, movement limits and spell bindings. The client validates rig coverage, marker alignment and required telegraph clips. Admit the encounter only when both can use a compatible revision. A running action retains its action and asset references until it ends. WM can stage and select a new revision at a fresh encounter, including changing an enemy move set or swapping a spell binding, through the same publish and rollback contract.

For example, `sword.light.1` binds a one-handed weapon family to a windup, one frontal contact window, recovery, stamina cost, an optional chain to `sword.light.2` and rig-specific clips. `swordsman.delayed_overhead` uses the same action schema with a long telegraph, facing lock, larger recovery and a distinct clip. `spell.projectile.1` binds to a learned spell through a server allowlist and has a release tick, interruption rules and an existing visual kit. The actual values are tuned in the encounter from timing traces and player observation.

### Runtime swap and rollback

Stage the combat DLL using the existing publication and health patterns. Validate the descriptor, input/output sizes, bounded candidates, enums, action IDs, numeric ranges and generation. Canary with a recorded snapshot and input. Commit between actions with no in-flight request, then release the old library when the host holds no borrowed pointers or callbacks. A failed candidate leaves the last healthy implementation active. If the active module fails, disable its proposals, reconcile from the server, and complete server-acknowledged mode exit before routing inputs back to stock combat. Never replay a committed hit during a client rollback.

Pin the authored revision for an active encounter. Admit a compatible staged revision at a new encounter or other agreed quiescent point, and roll back to the last accepted revision through the same handshake. Demonstrate same-process client A → B → A and module unload independently of server revision changes. The first server deployment may need one coordinated restart to add the authority seam. Server code replacement is a separate capability to design if switching the installed rules and live revision is insufficient.
