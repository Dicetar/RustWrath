# RustWrath architecture review and release plan

**Review date:** 2026-11-05. **Source baseline:** fetched main at `dbaf8eac`, Bevy 0.18.1. This is a source and requirements review. No build, server or gameplay run was performed. The recorder writer and pose rollback edits in the integration checkout are local proposals and must be reviewed against the release branch. The newer debuglocals and LFG cooldown commits are already on main; the older launch log cannot verify them.

## What counts as released

Use the two destinations in the approved completion plan, with the November owner decisions taking precedence on sequencing. **Replacement release** covers the full stock 3.3.5a client surface, required installed addons, WM observation and actions, supported live updates and recoverable Windows delivery. **Full platform** adds swappable movement, Souls combat, functional building, generated spaces and story. Northshire to the Elwynn boundary is the first integrated alpha gate. It closes neither release.

Evidence sources: [owner decisions](../baseline/owner-decisions.md), [existing requirements matrix](architecture-traceability.md), [compatibility ADR](adr-0001-wrath-compatibility-boundary.md), [module ADR](adr-0002-live-client-modules.md), [server and client seams](../baseline/seam-maps.md), [inventory issue](../../.scratch/project-b/issues/18-stock-replacement-inventory.md), and D:/WOW/PROJECT_B_COMPLETION_PLAN.md §§1, 8–10, 13. The November 3 execution packages supply the diagnostics and hotpatch sequences. The matrix is a historical baseline; do not reassign its October defects without checking HEAD. For example, the procedural artifact codec now exists and the quest-details decoder has been repaired.

## Weak sides in priority order

|Priority|Current evidence|Consequence and architectural decision|
|---|---|---|
|P0, fidelity|In app `wrath.rs`, `push_player_inventory_fields` explicitly copies 24/28 bank slots and 6/7 bank bags. `push_item_fields` maps an item into the smaller donor layout.|Correct packets can lose state before UI sees them. Make the Wrath domain owner lossless, migrate readers a workflow at a time, and keep donor projections only for remaining callers. Never add four slots at donor offsets occupied by other fields.|
|P0, release coverage|Issue 18 still has open acceptance boxes. The existing 17-family matrix explicitly lacks an exhaustive behavior denominator.|A green alpha can conceal unsupported features. Build the inventory from pinned server handlers, FrameXML consumers, profile corpus and required addon versions. Give each row a receiver and an acceptance scenario.|
|P1, session overload|The app creates the worker event feed with `crossbeam_channel::unbounded()` in `wrath.rs`. `wrath_net_drain`, `wrath_dispatch_events` and `wrath_apply_world` coordinate delivery and mutation.|A stalled consumer can accumulate events. Define capacity, ordering, lifetime and overload behavior by message class. Scope retirement and disconnect must still make progress when the consumer stalls. This is a source risk; memory exhaustion was not observed.|
|P1, update ownership|The command tap, dispatch and projection live in the same app integration file. One change to a quest, item or spell can touch wire semantics, normalized state, ECS projection, UI delivery and diagnostics.|Keep the session epoch and world generation in the resident host. Decode once, update one authoritative domain owner, then publish a read-only view. Extract by migrating actual consumers; moving functions among files alone does not fix lost state.|
|P1, gameplay modules|The production loader in `benilla-hotpatch` opens the pose entry point and validates pose batches. Search for `ModularGameplayRegistry` found its definition and test; no production caller in the crates searched.|A gameplay toggle does not install, activate or retire a processor. Establish the lifecycle on movement first and require each additional seam to have a real caller, state contract, failure policy and baseline fallback.|
|P1, live revision consistency|`Profile::reload`, `ProfileAssetReader::reload` and `run_pending_reload` are separate entry points. ADR-0002 explicitly distinguishes reopening archives from refreshing already loaded assets.|A candidate can be valid on disk while a visible model, catalog or Lua VM still consumes its predecessor. Stage all affected consumers and swap their revision together at a safe boundary.|
|P1, UI compatibility|The recent run reached stock call sites without the expected function or return type. Two high-volume cases received later fixes on main. A reporter error can also amplify another error.|Track the caller, real data owner, Lua signature, event ordering and protected-state rules together. Implement behavior in the owner and project it to Lua. Error frequency alone is a poor release priority.|
|P1, external authority|The procgen crate has `Candidate::{capture,encode,decode,restore}` and `WmDraft::{build,verify}`. The server seam map identifies placement, collision, navigation and instance lifecycle as different capabilities.|An offline artifact can be correct while players and creatures disagree about traversable space. WM/server must own durable publication, entity IDs and outcomes. Client previews remain provisional until acknowledged.|

## Who writes what

|State|Writer|Readers and transition rule|
|---|---|---|
|Session/world identity|Resident session owner|Attach identity at capture. Check it before mutation, retire old pending work on transfer and reconnect.|
|Inventory, XP, quest progress, spell and pet state|Wrath reducer/domain owner from authoritative server updates|UI, rendering, addons and diagnostics read projections. A successful outgoing write is not server acceptance.|
|Local motion prediction and correction|Resident movement controller with server reconciliation|Optional module proposes permitted intent. Host checks capability, clamps or rejects, emits wire commands and reconciles once.|
|UI VM, input capture, rendered scene|Resident UI and world hosts|A VM or module can be replaced without taking ownership of the socket, GPU resources, GUIDs or persistent character state.|
|Published content and gameplay authority|WM and server for approved definitions, collisions, rewards and spawns|Host admits a versioned publication; running instances pin a revision until migration or completion.|

## Execution sequence

Names in backticks below are current source entry points unless marked **proposed**. Proposed functions describe responsibilities and outcomes; implement them in existing owners wherever possible. Gates are future verification work for an authorized run.

### 0. Establish the release ledger and reproducible baseline

1. Extend issue 18, using C01–C17 and the 17 compatibility families as parents. Enumerate each independently observable operation from the pinned 12340 handlers, Lua callers/events, required addon manifests, asset variants and owner workflows. Map each operation to its encoder, decoder, reducer, UI/scene reader and existing case or missing case. Record normal, refusal, reconnect, persistence and unsupported-server evidence where applicable.
2. Keep capability status (working/partial/broken/unknown) separate from evidence (source, compiled, focused check, server receiver, visible behavior). Require revision, executable identity, profile, server mode, addon versions and scenario with every promotion. Associate debug snapshots with launcher stderr from the same run. Count matching log lines separately from unique actions.
3. Reconcile local recorder/pose changes as separate work items. For pose, review `Host::poll`, `Host::evaluate`, Bevy `apply_pose` and `restore_pose` together. Exercise malformed host input, candidate refusal, multiple failed predecessors, and A → B → A. For export, review `History::export` and `export_sync` under overlapping manual save and exit.

**Exit:** a pinned baseline and named owner for each gap; a repeatable route and installation manifest. The inventory continues alongside alpha work; no “percent complete” until its denominator is reviewed.

### 2. Replace lossy projections and close the baseline families

Start with inventory as the reference migration. Add **proposed** `apply_wrath_inventory_delta` in the inventory owner using typed slot/bag addresses, preserving absent fields, explicit clears and container ownership. Route `push_player_inventory_fields`, `push_item_fields`, bag access, bank UI, item commands and Lua queries through that state. Compare old and new readers on the same scoped updates, migrate remaining callers, then remove the narrow projection where unused. Gate on slots 25–28, seventh bank bag, transfer between bags, delayed templates, clear and reconnect. Repeat this pattern for authoritative XP, pet ownership and class state only where the inventory shows a real loss.

**Exit:** every required behavior has a pinned, repeatable acceptance case. A prefix of opcodes decoded, a mock-loaded DLL, or the absence of a Lua exception cannot close a family.

### 3. Ship WM integration and coherent live updates

1. **WM observation/action (C01–02, C13).** Follow `send_and_ack`, `poll_peer`, `wrath_wm_action_intake`, `send_action_result`. Validate scope, capability, expiry and idempotency before dispatch. Keep the ordinary wire path unchanged when negotiation is absent. Prove receiver consumption, player override, stale observation, timeout, fallback transport and reconnect on the owner's server.
2. **Live behavior publication (C14–15).** In the existing WM owner, implement or locate **proposed** `stage_definition`, `activate_revision`, `pin_instance_revision`, `rollback_definition`. Use Spellwright for the first change. Validate dependencies before publication, preserve the old instance's semantics, and reconcile retries by revision ID. Gate: A and B behavior on connected clients, old instance completes correctly, rollback selects A without a routine restart.
3. **Content and UI transaction (C16–17).** Compose `Profile::reload`, `ProfileAssetReader::reload`, dependent catalog/GPU owners and `run_pending_reload` behind **proposed** `stage_content_revision` / `commit_content_revision`. Identify affected consumers and their previous revision, reject partial preparation, publish at frame boundary, retain prior handles until success. Use signed/authorized manifests for remote distribution under an adopted trust contract. Gate bad manifest, missing texture, UI load failure and disconnect mid-publication; each yields either coherent old or coherent new content.
4. **Replacement release candidate.** Freeze the ledger and run the named baseline/extension scenarios against the same executable. Rehearse clean install, upgrade, offline startup, failed update and rollback with compatible configuration, profiles, addons, WM schemas and persisted characters. Preserve the previous installation. An owner decision is needed for exact addons, target hardware budgets and maintenance-restart exceptions.

**Platform gate:** run a combined scenario with movement, combat, building, generated content and story enabled, disable each independently, and repeat under reconnect and rejected updates. Record who owns outstanding timers, requests and memory after unload. The second release requires this gate plus the replacement release.

## Dispatch and evidence policy

Start two independent packages: **A**, release inventory plus the inventory projection migration plan; **B**, bounded session delivery plus the reproducible alpha route. Assign one integration owner to review changes touching `wrath.rs`, record source identity and own runtime slots. Then close the route, broaden parity by family, and integrate negotiated live updates. Offline module or procgen work may proceed in parallel; schedule live gameplay expansion after alpha per the owner decision. Server-side packages require their own approved workspace and owner.

For every package record existing/proposed function, input, writer, downstream reader, failure/rollback semantics, relevant build and evidence. Implementations are accepted separately at source, compilation, focused-case, receiver and visible/persistence levels. Only run builds, tests or client sessions when authorized. Split release work by independently observable behavior; revisit this plan when a verified implementation or explicit scope decision changes a gate.
