# WM encounter drafts and receipts

Source-only implementation in `wm_draft.rs`; not executed or compiler-accepted. It reuses `wm.world.bundle.v1` and native `creature_spawn` / `creature_despawn` contracts inspected in `D:/WOW/wm-project/src/wm/world/bundle.py`, `world/tools.py`, `sources/native_bridge/payload_contract.py`, the action catalog, and `native_modules/mod-wm-bridge/src/wm_bridge_creature_actions.cpp`. No WM file is changed and no second publisher/runner is introduced.

`WmDraft::build` verifies the full candidate and rederived encounter plan. Options require explicit bounded namespace/run key, duration 1000–600000 ms and actor budget 1–512. A larger plan is refused completely, not truncated or silently split across runs. The draft has a `bundle` member in the existing owner's format; the outer `project-b.procgen.wm-draft.v1` package retains scope, plan identity, cleanup requirements and preflight policy. It is deliberately not itself a runnable bundle document.

Each spawn supplies an existing creature entry, exact x/y/z/orientation/map, unique run-qualified arc key, fixed duration, `follow_player: false` and `use_template_faction: true`. Template services and actual levels remain external preflight responsibilities; no service or level mutation is emitted. There are no permanent database spawn actions, fabricated server IDs, stock spell carriers or client geometry changes.

The inspected native owner resolves the online player, places summons in that player's current map/instance and copies the player's phase. Its request does not enforce the proposal's instance/phase/world generation. Therefore `requires_owner_preflight` always remains true: OC/WM must check current scope and authorization before extracting/executing the nested bundle. The existing runner also accepts a player GUID and run key separately; they must match this package. This library does not grant execution permission or add scope enforcement to WM.

`import_report` consumes a retained JSON result from the existing runner, verifies bundle/run/mode, contiguous step prefix, stop-at-first-failure ordering and aggregate status, and normalizes outcomes. Confirmed application requires both coordinator `applied` and matching native `done`/`creature_spawned` result, correct player/entry/arc key, actual positive supported ObjectID and live GUID, and no duplicate ObjectID. Enqueue/transport success alone is insufficient. A nominal success without a usable matching identity remains unknown, preserving earlier receipts. Failure/exception also remains unknown because mutation may precede response loss. Unattempted trailing steps are distinct. Dry runs only produce preview outcomes.

The receipt retains the complete proposal scope, bundle/run, per-step local identity, actual returned IDs and fingerprint of the original report bytes. FNV and caller-supplied reports are not authentication. `ApplicationReceipt::verify` requires the retained report and reimports it through the verified candidate/plan/draft, rather than trusting edited receipt JSON.

`cleanup_draft` produces reverse-order native despawn steps only for confirmed owned ObjectIDs and separately lists every unknown step for owner reconciliation. It never guesses IDs from arc keys or local generated identities. A preview cannot produce cleanup. No confirmed IDs yields no bundle, while unresolved effects can still require reconciliation. Cleanup is another ordered, potentially partial operation; creation of its draft does not prove deletion. Timed expiration likewise does not prove the ownership row was retired or an ID is reusable. Existing WM ownership/retirement policy remains authoritative.

Retain candidate, supported source archive, placement request/plan, draft, exact original WM report, normalized receipt, and subsequent cleanup reports. Never replay a complete or partial spawn bundle automatically. For unknown effects the existing owner must inspect the scoped native requests/world-object records and decide reconciliation. Partial cleanup requires the same per-result discipline. This layer neither executes those reads nor clears uncertainty from a timer.

`ApplicationReceipt::import_cleanup_report` also normalizes the existing owner's cleanup report against the rederived reverse-order cleanup bundle, requiring a distinct explicit cleanup run key. Each returned ObjectID is confirmed removed only for matching coordinator-applied/native-done `creature_despawned` evidence. Missing/mismatched/failed responses remain unknown; trailing steps remain unattempted. The normalized cleanup receipt retains unresolved spawn steps and a reconciliation flag. A reported aggregate `complete` alone cannot clear uncertainty.
