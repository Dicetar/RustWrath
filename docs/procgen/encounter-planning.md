# Encounter planning API

`planning::EncounterPlan::build(candidate, supported_build, request)` turns a validated owned candidate into a complete deterministic proposal. `encode` and `decode` require that candidate/build and rederive every planned actor. The plan has its own `project-b.procgen.encounter-plan.v1` schema and fingerprint. No file, network, WM, database or game operation occurs in the library.

The placement request schema is `project-b.procgen.placement-request.v1`. Required fields are defined by the strict DTO in `planning.rs`: candidate manifest, explicit revision, player/map/instance/phase/world-generation scope, domain transforms, actor-kind template bindings, world bounds and minimum horizontal separation. It is not an executable WM action. All floats use the artifact API's bit strings; identities use the same fixed-width hex convention.

Each populated domain needs exactly one transform. Local X and Y map to explicitly supplied independent world XY vectors, avoiding guessed handedness or rotation. Height is explicitly flat relative to origin Z, scaled generated terrain relative to origin Z (overworld only), or an absolute Z grid with exactly the domain's dimensions. Neither flat nor generated terrain heights imply that the stock map has ground there. Both domains currently target the one pinned world scope; their local encounter IDs remain unchanged and their positions are checked together for spacing.

Bindings match the complete actor kind, including enemy archetype/boss flag or NPC role. Each binding pins an existing creature entry, retained database snapshot/record hashes, supported level interval and declared configured services. NPC roles require a corresponding service declaration. These are caller-supplied capability claims requiring owner preflight, not independent database verification. Planning does not allocate templates, adjust creature levels, create vendor inventories/quests or configure NPC flags. Missing mappings or incompatible levels fail the complete proposal.

Actors retain input order, source index, domain and encounter group. Local IDs combine the candidate fingerprint, domain and input index; they are not server identifiers or security identities. Cross-candidate identity additionally requires the retained source/candidate pin. Boss/add encounter groups are preserved exactly, including the generator's separate boss and add groups. There is no inferred grouping or silent repositioning.

Transforms must be finite and nondegenerate; axes are bounded. World bounds are explicit, ordered and within +/-1,000,000 units as an allocation/arithmetic guard, not a declaration of valid WoW map coordinates. Minimum horizontal separation is zero (explicit overlap permission) or 0.001–1000 world units. Nonzero spacing uses a bounded spatial grid and rejects collisions across domains. Positions are checked after conversion to the actual f32 representation. A failure returns no partial plan.

Every plan carries `requires_owner_preflight: true`, regardless of any supplied placement review locator. Existing WM owners must verify live player/map/instance/phase/generation, template revisions, actual actor levels/services, collision, navigation, visibility, encounter safety and authorization before applying a draft. A candidate, a review locator and a matching FNV hash cannot grant those properties.

Source-only implementation; no builds, tests/new test cases, generator invocation or live checks were run. Pending cases include missing/duplicate mappings, wrong scope/candidate, degenerate axes, height-grid mismatch, float conversion boundaries, explicit overlap versus spacing refusal, same-scope cross-domain collisions, stable order/identity and imported plan tampering. Runtime placement remains UNKNOWN.
