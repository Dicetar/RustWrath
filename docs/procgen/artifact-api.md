# Procedural candidate library

Source implementation, not compiler or runtime acceptance. No checks or new tests have been run/created for this implementation. The architecture ADR remains Proposed. Full stock-client replacement remains open.

`artifact::Candidate::capture(spec, output, source_identity)` takes an existing generated result and produces an owned candidate. `encode(supported_build)` returns bounded JSON bytes. `decode(bytes, supported_build)` returns a validated candidate; `restore(supported_build)` rebuilds the existing generator output using supported static catalog references. These functions perform no file, Git, network, WM or server operations and do not regenerate the request. The caller supplies a retained supported build identity; the library does not independently attest the archive's contents.

The implemented schema is `project-b.procgen.candidate.v1`. This is the first implemented encoding; the earlier `artifact-handoff.md` is design history, not another supported wire representation. Rust DTO field names in `artifact.rs` are authoritative. Request seed, item IDs and the manifest are fixed-width lowercase 16-character hexadecimal strings. Every float is an eight-character IEEE-754 bits string, including request frequency and sea level, item stats and terrain samples. Enum names use snake case. Native ordered room graph and tile sequences are preserved. Unknown fields, duplicate keys, unsupported versions and malformed hex fail explicitly.

The candidate retains the full request, effective item center level ten, all item fields, the complete ordered built-in part catalog (including unused definitions), dungeon, terrain and actors. `source_identity` requires repository, full Git commit, retained source archive SHA-256 and dirty state. `catalog_identity` carries a separate catalog version and full-catalog FNV fingerprint. Restoration requires exact catalog definitions and identity. No imported strings are leaked or installed as static catalog entries. Original generator-v2 output and manifest encoding are unchanged.

The complete existing v2 manifest is recomputed after restoration. FNV is an inconsistency check, not a signature or proof that the specified generator produced the data. Build identity is matched to the caller's supported pin, not trusted merely because it appears inside the candidate. Archive retention, cryptographic archive verification and supported-build policy belong to the caller.

JSON is capped at 64 MiB. A structural pass before typed allocation rejects nesting beyond 16, more than 4,300,000 values, arrays above 1,048,576 entries, objects above 64 keys, keys above 128 bytes, strings above 1024 bytes and total decoded strings above 64 MiB. Typed semantic validation then applies request limits, exact array lengths, catalog equality, item count/parts/stats, bounded reciprocal connected room graphs, disjoint walkable rooms, tile reachability, normalized finite terrain, safe entrance, boss rules, actor coordinates/domains and level/count bounds. The envelope budget can reject an otherwise valid generator request whose combined output exceeds the persistence budget; callers must handle refusal rather than assume every maximum-sized request fits.

Validation errors expose a stable subsystem field and explanatory reason through the existing `ValidationError`. A candidate that passes these checks is data-consistent. Placement, collision/navigation, template services, server approval and publication remain separate responsibilities.

Pending authorized verification: compile library and CLI; capture/encode/decode/restore a pinned generated candidate; compare every float bit and ordered field; reject truncated/duplicate/unknown/oversized input, invalid graph/room/actor references, wrong build/catalog and changed manifest; exercise single-room/zero-density and upper-bound requests. These are prepared cases, not newly written or executed tests.
