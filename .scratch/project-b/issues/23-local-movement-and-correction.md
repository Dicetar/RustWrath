### Tickets opened by this survey

1. `oc/movement-correction-while-moving` — Server correction (MSG_MOVE_TELEPORT_ACK or spline snap) must be applied to the local player even when locally moving, not only at rest. The gate in `wrath.rs:10823` (`server_flags & MOVING == 0 && local_flags & MOVING == 0`) contradicts the reference (`Movement.cpp:OnTeleport`, `UpdateStatus`) which applies server-authored poses unconditionally. Files: `crates/benilla-app/src/wrath.rs` (translate_gameplay), `crates/benilla-app/src/player/wire_in.rs` (apply_self_move for self-addressed moves). Acceptance: a moving player receives a near-teleport correction; the local pose snaps to the server position within one frame; the correction is traced with distance_bucket. Named test: `a_moving_correction_snaps_pose_and_traces`.

2. `oc/movement-tolerance-config` — The reconcile tolerance (RECONCILE_TOL_SQ) and correction distance_bucket thresholds are hard-coded constants. Add a configurable tolerance record (per session/realm) loaded before live comparison, with the chosen values traced. Files: `crates/benilla-app/src/net/motion/remote.rs` (RECONCILE_TOL_SQ), `crates/benilla-app/src/wrath.rs` (distance_bucket), `crates/benilla-app/src/quest_trace.rs` (Stage::MovementCorrectionApplied). Acceptance: a config file or resource sets the position tolerance and distance buckets; the values appear in the trace at session start. Named test: `tolerance_config_loads_and_traces`.

3. `oc/forced-movement-mode-audit` — Inventory and apply the unsupported forced movement modes from handoff 2026-11-15-wrath-movement-gaps.md (can-fly, gravity disable/enable, spline flying/gravity). Each must either be applied (with a consumer in the shared controller) or explicitly documented as not applicable to the selected scenario. Files: `crates/benilla-app/src/net/gameplay/mover_control.rs` (parse), `crates/benilla-app/src/net/gameplay.rs` (translate), `crates/benilla-app/src/player/state.rs` (MoveModes). Acceptance: a checklist in the handoff marks each opcode as applied/acked or deferred with reason. Named test: `each_forced_mode_opcode_decoded_and_acked_or_deferred`.

4. `Blocked: needs owner run` — Acceptance line "Demonstrate walk, stop, turn and jump on the selected tile; required movement flags and acknowledgments are correct" requires a live client/server to verify the server's ack sequence (MSG_MOVE_START_FORWARD → HEARTBEAT → STOP, jump tail with correct fallTime, turn SET_FACING throttle) and visible movement on the tile. Source and tests cover individual edges but not the end-to-end tile scenario with a real AzerothCore server.

5. `Blocked: needs owner run` — Acceptance line "Choose and record discrepancy/latency tolerances before live comparison" requires the owner to drive the character, observe correction distances, and confirm the chosen tolerance bands match live behavior. The source-observed vs predicted position distinction exists in code (RemoteMotion.last_apply_pos vs wow_pos) but the "choose and record" step is a manual owner action.

6. `Blocked: needs owner run` — Acceptance line "Honor required forced movement/root/speed state for the selected scenario" requires live verification that root grant mid-move stops the mover, hover grant jumps, feather fall reduces terminal velocity, and water walking allows crossing liquid. The code path exists but the "selected scenario" (Northshire tile) is only testable in game.
