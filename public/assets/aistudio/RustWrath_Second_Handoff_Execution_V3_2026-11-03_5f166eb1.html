Evidence levels required in every ticket

  1. S · Source: relevant code and interface inspected at exact SHA.
  2. B · Build: exact command, target, features, log, exit code and binary hash.
  3. T · Focused test: actual input, expected and observed output, regression fixture, result.
  4. R · Runtime/receiver: a real running producer/consumer or module accepted an event in the intended environment.
  5. V · Visible gameplay: the owner saw the requested interaction and actual state outcome in the running client.

A task can be source-reviewed yet remain unverified at B/T/R/V. Save these five levels independently for each affected feature and each hotpatch revision.

03 · ARCHITECTURE

The resident observation plane

Use the established client ownership graph. Place the flight recorder in the host with a small typed interface. It observes game events without becoming another authoritative state store.

IntentUI input, hit test, Lua and action guard
OutboundCommand channel, outbox, serialization
WireActual socket writer and receive
ServerAzerothCore authority
ProjectionWrath decoder, reducer, ECS
DisplayQuest, journal, UI, rendered frame
IFR holds bounded structured evidence; GCV evaluates state-machine contracts; PRM records build/revision/activation/rollback. Every outcome includes scope and evidence confidence. Only the server provides authoritative durable gameplay outcomes.

Proposed component boundaries (design, not existing filenames)

diagnostics-core

Typed event/schema, in-memory ring, incident sink, correlation, immutable snapshots. Unit-testable without Bevy. May begin as an app module if RFC favors it.

diagnostics-adapters

Lightweight probes at Wrath action/worker, quest/UiScript, asset and hotpatch seams. Keep game logic free of dynamic recorder dependencies.

diagnostics-UX

egui inspection pane, sanitized export and optional screenshot. Report generator operates on copies outside frame-critical execution.

Event delivery rules

  • Record monotonic event_seq per client host; include run_id, session_epoch, world_generation, entity/domain IDs and selected protocol mode.
  • Tag exact layer ownership: intent, channel_admitted, outbox_admitted, socket_write_completed, packet_received, decoded, authoritative_replica_delta, ui_event, render_checked.
  • Use bounded buffers and explicit drop counters. Critical gameplay events remain in their owning reliable queues; diagnostic telemetry may sample or drop, with loss reported.
  • Retain host diagnostic history across Lua VM resets. Close in-flight actions on disconnect/world change as cancelled or superseded according to scope.

Correlation mechanism

Mint the local interaction_id at the input/action boundary; propagate it only through **internal client interfaces**. Standard WoW 12340 server packets lack a universal action-trace field. Match incoming results using session/world scope, player/NPC GUIDs, quest/spell/item IDs, operation type and ordered evidence windows. Return exact, strong, heuristic, ambiguous or unmatched. Never promote a heuristic match into a definitive server acknowledgement.

Readiness check for diagnostics

  • Red/green source fixtures for queue-full, disconnect, duplicate same-NPC clicks, response after worldport, Lua reload and delayed reward.
  • Event loss counters and time/size budgets verified under bursts. Metrics labels remain low cardinality (subsystem and outcome; IDs belong in trace records).
  • Recording enabled behind bounded configuration; incident export is redacted and available even when the UI reboots.
  • One owner-visible negative and one positive questgiver case produce useful first-failing-boundary reports.

06 · UI DIAGNOSTICS

How to diagnose a button that “does nothing”

1. Pointer target

Actual hit test, local bounds, topmost frame, transparent/intercepting overlay and egui pointer capture.

2. Script dispatch

Was OnClick/OnEvent registered and invoked? Record Lua load, handler and method errors.

3. Client guard

Has questgiver state, active character, action latch or selected UI version refused the action?

4. Transport

Record admission, writer and relevant response; report precise missing link.

5. Display state

Inspect view model, visibility, layout/clip rect, render ordering and stale resource handles.

6. Evidence UX

Offer click-to-copy last trace, redacted packet metadata and optional screenshot, with no mandatory user narrative.

Store UI errors in the host across VM reload. The existing UiScript diagnostic log retains 256 distinct errors within a VM and resets when a new UI VM is constructed. Keep a scoped deduplication key so repeated handler failures remain visible without overwhelming the journal.

07 · LIVE PATCHING

Patch Revision Manager: capability before convenience

The existing pose loader supports trusted, local, versioned DLL publications and candidate output validation; actual same-process rendered acceptance remains outstanding in ADR-0002. All reload classes need their own proven activation/recovery contract.

ClassSnapshot maturitySafe targetRollback limits
Pose ABI1 DLLHost, adapter and publisher source exists; focused round-trip passes by repo reportSame-process swappable postprocessor after candidate validationRecoverable candidate/output error; native memory crash requires restart.
WGSL shaderOpt-in watching; rendered acceptance pendingReload compatible shader and keep prior working pipelineTransactional pipeline validation needs proof.
Lua/XML/addonExisting /reload VM lifecycle; developer content overlay pendingVersioned overlay → controlled /reload → rebindRebuild UI VM; preserving network state needs runtime proof.
Textures, M2/SKIN, animationsCoherent dependency revision and rebind still plannedStaged family swap, unchanged logical entityRevert complete family and discard stale jobs.

Patch activation state machine

built → staged → authenticated/local-trusted → ABI/dependency checked
      → candidate validated → activated → observed healthy → accepted
                ↘ rejected → preserve active
activated → recoverable fault → rollback last-good and mark bad revision
process crash → launcher recovery on next start (no in-process guarantee)

Proof requirements: log active module revisions, manifest identity, binary PID/hash, unchanged session/world identity, visible difference B and restoration A, error/latency measurements, and original-state restoration. Failure injection: invalid ABI, missing/late DLL, locked file, malformed manifest, repeated revisions, output with NaN, incompatible shader and /reload asset failure where applicable. Keep the active module until replacement validates.

Trust boundary: a local SHA-1 filename validates identity/completeness of the selected file, while publisher authentication is a separate requirement for any future remote distribution. In-process native DLL code is trusted executable code and can crash/corrupt the host; arbitrary untrusted patch delivery is outside this program.

Future WM pilot: the current benilla-wm-native path is bounded/authenticated loopback observation transport, and cannot be treated as an already implemented remote patch publisher. Extend by explicit capability negotiation, opt-in, authenticated packages and rollback scopes.

Operational guardrails from RustWrath

  • One accountable owner per ticket; coordinate AutoSwarm/multiple agents only after reading the project's current skill and ownership record.
  • One owner for the shared Cargo build slot and one for the graphical client slot. Do not interrupt a running session, overwrite dirty work or use blanket staging.
  • Use only authorized targeted checks; the project's then-current grant caps essential targeted test cases per task at 20. Reconfirm the grant before execution, and avoid filling the quota by habit.
  • Existing game install, server databases, auth credentials and preserved build-12340 reference remain read-only unless the owner assigns otherwise. Player drives login and combat; no unattended persistent character mutations.
  • Do not claim a complete 3.3.5 client based on one Northshire flow. Retain explicitly labeled gaps for full stock replacement and experimental modules.
  • Performance budgets for event emission, allocations and patch activation must be measured on the actual target hardware before assigning numerical thresholds.

09 · AGENT PLAYBOOK

How one agent should execute each work package

  1. Read source-of-truth docs — AGENTS.md, CONTEXT.md, workflow, active ownership, selected ADR and current ticket. Check Git status, HEAD, dirty files and live build/client slots.
  2. Load only relevant skills — use the project-installed project-b-12340-reference if available for Wrath behavior, AutoSwarm only if delegating, and targeted workflows from the named public skills below.
  3. Define a vertical symptom/proof — one action, one failing boundary, one test before implementation. Call out proposed interfaces and avoid inventing APIs.
  4. Work RED → GREEN → review — reproduce, test failing expectation, implement smallest fix, rerun focused checks; inspect all diffs and evaluate security and protocol effects.
  5. Respect permissions — compile or run client only with current slot ownership and authorization; owner controls real gameplay. A documentation-only task should need no live execution.
  6. Close with evidence — classify source/build/test/runtime/visible proof separately; record unresolved limitations, regression fixtures, task state, changed files and exact next ticket.
