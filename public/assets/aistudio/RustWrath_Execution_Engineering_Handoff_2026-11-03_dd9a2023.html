DESIGN NOTE · Purpose & status

Mission, scope and status

Mission. Convert the prior RustWrath architecture review and general handoff into a small, dependency-ordered, executable engineering backlog that a coding agent can implement one bounded ticket at a time. Deliver evidence-based private Windows alpha reliability, a persistent Interaction Flight Recorder (IFR), Gameplay Contract Validator (GCV) and a safe, capability-scoped Patch Revision Manager (PRM). The first gameplay proof is Firna's Northshire quest → combat → loot → reward journey.

Provenance. This document was created from (1) the attached 2026-11-03 conversation export, (2) the attached General Technical Handoff, and (3) read-only checks of current public wotlk repository rules and project documents. Detailed defect claims remain anchored to the prior static review at 236b1a7aebc017655f9a0fc0dea54e52dae891ef. The live checkout, uncommitted work, local server, selected game assets and runtime have not been inspected in this handoff. Revalidate every file/function and current bug at execution time.

Execution boundaries inherited from the repository. One ticket owner across any necessary crates; one shared Cargo slot and one graphical-client slot; no competing live login; credentials and combat are owner-driven; original game installation, decompilation and server files are read-only unless separately assigned; at most 20 essential targeted checks per task under the existing grant. Documentation-only work requires zero builds. Review the current AGENTS.md, CONTEXT.md, docs/agents/workflow.md, active-ownership.md, owner decisions and local handoffs before beginning.

Maturity warning. A declared ABI, an API function, a successful build, a unit test and a web preview establish different claims. Full live gameplay and reliable hotpatching remain subject to recorded receiver-level and user-visible acceptance. The earliest real alpha blocker has priority over speculative platform expansion.

Output contract

Each implementation session should produce exactly one ticket closeout: source revision and dirty paths; owned diff; test names and actual outputs; measured or missing runtime evidence; regressions protected; unresolved questions; the next unblocked ticket. No invented build, game, server, visual or patch outcomes.

Recommended package boundaries: add diagnostic types/correlator/collector inside the smallest existing reusable Rust owner (new crate only after the D00 RFC proves a cross-crate need); keep contract validators near each domain; keep the event store resident outside the Lua VM; attach a UI inspector to existing developer tools; keep PRM native and separate from the recorder. Design small stable interfaces and keep dependency flow one-way. Modules call into a narrow recorder API; the recorder never imports the quest/UI domain wholesale.

Version semantics: Vanilla donor, 3.3.5a baseline, and capability-negotiated experimental mode are separate. All wire compatibility questions start with the pinned 12340 reference and relevant AzerothCore source. Developer trace IDs remain local/sidecar; no extra bytes enter baseline stock packets.

The architecture tension to decide in D00

A new shared diagnostics crate isolates schemas but adds cross-workspace integration cost. An app-local module is faster for the first vertical slice but risks coupling if event producers span many crates. The RFC must examine existing tracing/journal/event constructs and choose deliberately. Prefer data-only public interfaces; higher-level domain interpretation stays with the owning validator.

Example identifiers and values above are synthetic. Every exported run also has a metadata record: wall-clock start, source SHA and dirty marker, actual running binary digest, server revision when known, selected asset profile, active module/content revisions, platform and config feature gates. Missing hashes are null, never copied from unrelated Git state.

Telemetry vocabulary. Observed boundaries: intent, ui_handler, command_admitted, outbox_admitted, serialized, socket_written, inbound_decoded, server_state_observed, model_projected, ui_presented. A server reply may be ambiguous; class a refusal only when protocol or validated guard explicitly carries the reason. Outcome categories: observed_success, expected_refusal, command_refused, timeout_unverified, state_mismatch, presentation_mismatch, script_or_render_error, ambiguous, cancelled_or_superseded.

Correlation confidence. exact = direct internal action identity; strong = unique protocol/domain keys and state transition; heuristic = time/order-proximity; unmatched = no safe claim. Maintain maximum concurrency, timeout, and duplicate suppression. Correlate with (run_id, session_epoch, world_generation, operation, entity/quest IDs, event sequence, window). Stock 12340 generally lacks a universal request identifier; preserve uncertainty. Clock logic for contract tests must be deterministic and injected.

Quest acceptance contract

Click → handler/guard → QuestgiverAccept channel admission → outbox acceptance → socket writer → observed quest-active slot OR explicit refusal → journal state → journal row. Every missing stage yields an incident with the last verified boundary. A missing downstream event is initially timeout_unverified, with thresholds informed by measured latency; an observed authoritative row and missing UI row can establish presentation_mismatch.

Quest reward contract

Completion notification, inventory updates, money/XP changes, quest removals and chain continuations can arrive separately. Confirm appropriate server-backed deltas, allow legitimate zero XP at cap, item choice/inventory constraints, and asynchronous update ordering. A SMSG_QUESTGIVER_QUEST_COMPLETE alone is insufficient evidence of all rewards.

Reload and patch state machines

  • VM reload: ActiveUI → TearDown → Recreate → Rebind → Ready, with host recorder intact, stale frame identities invalidated and pending interactions cancelled/rebased by policy.
  • Pose patch: ObservedManifest → Staged → Preflight → Validated → ActivationAtSafeBoundary → Active, or RetryableFailure → Backoff → Retry, or Rejected while last-known-good stays active. Maintain activation audit and next-start crash fallback.
  • Content family (future): immutable revision manifest → complete dependency closure → async stage → reject stale loads → ready barrier → coherent activation → validated / revert. Models and .skin dependencies share one revision. Terrain/collision require separate authority contract.
DESIGN NOTE · Agent operating procedure

Agent operating procedure: one small task at a time

  1. Admission. Read the repo's AGENTS.md, CONTEXT.md, docs/agents/workflow.md, latest owner decisions, active-ownership.md, current ticket and local .scratch/project-b/handoffs. Recheck working tree, indexed changes, jobs/processes and actual build/client reservations. Never blindly use the dated examples in this document.
  2. Discovery. Map the call chain for this ticket, identify the domain authority, version boundaries, existing fixtures and smallest observable proof. Consult the correct source class before inventing semantics.
  3. Ticket refinement. Convert a coarse task into 2–7 ordered microsteps with exact existing files, one expected red test, one implementation action, one verification result and one source-labeled artifact. Change the path list if source reality differs; record why.
  4. Build first evidence. For bugs reproduce the original symptom or a faithful fixture, capture red output, and isolate failure. For new capability define failing contract. Treat unexpected failures as investigation work rather than hiding them.
  5. Minimal implementation. Prefer a vertical tracer bullet through real owners. Keep code readable, typed and robust to malformed input; preserve 12340/Vanilla mode isolation. Do not widen ticket scope to unrelated repair candidates.
  6. Verification. Run the minimum authorized named targeted cases. Only the coordinator holding a resource slot may build/run. Include load/performance checks for hot-path or patch tasks; compare with baseline.
  7. Review. Check spec compliance, actual diff, cross-crate ownership, error paths, user-facing effect and unsafe/FFI implications. Use security review for parser/patch boundaries.
  8. Handoff. Update owning ticket, local evidence and plan/progress files. Record DONE, PARTIAL, BLOCKED or UNVERIFIED accurately with checks run/unrun and a precise next step. Committing/pushing is a distinct authorized action.

Work-in-progress limit: one active implementation task per local session by default. The repo supports AutoSwarm collaboration under its coordination rules when explicitly authorized and resource owners are assigned. One-machine sequential execution remains a safe default. Never invent delegated/parallel results.

Task split rule: If a change spans several independent outcomes, divides across more than one meaningful boundary, or cannot be verified with a small fixture, split it into a parent design task plus independent follow-on tickets. If an existing ticket has a live owner, coordinate or choose another unblocked ticket. A “ready frontier” means all dependency IDs are completed with appropriate evidence and ownership is available.

Session files

  • task_plan.md: active ticket and phases (or existing planning plugin's project-scoped equivalent)
  • findings.md: evidence references, relevant symbols, competing hypotheses and research discoveries
  • progress.md: what was tried, what passed/failed, actual commands/output and precise resume step
  • .scratch/project-b/issues/<NN>-<slug>.md: durable local ticket (per project rules)
  • .scratch/project-b/handoffs/<date>-<ticket>.md: completed outcome/evidence log, as configured by repo

Planning plugin files are typically gitignored; promote enduring decisions into an ADR, tracked test, code or approved ticket, rather than relying on a temporary scratch plan.

Native hotpatch limitation. A trusted in-process DLL can still panic/abort/corrupt memory. Preflight, ABI checks and rollback cover recoverable errors; process-level crash recovery requires last-known-good on next start. Automatic rollback from arbitrary in-process memory corruption cannot be guaranteed.

Diagnostic influence limitation. Adding synchronous logs can create frame stalls and alter race timing. Sampling and caps must be explicit; dropped telemetry should cause partial_trace / confidence downgrade, preserving correct negative findings. Use actual measured budgets and report them, rather than inventing universal FPS or latency thresholds.

Architectural milestones: Stage 0 stabilizes actual alpha blocker and code admission/CI; Stage 1 builds resident diagnostic infrastructure; Stage 2 proves quests; Stage 3 validates pose patch reliability and staged UI changes; Stage 4 extends coverage, hardens release evidence and explores remote WM publishing only behind authorization. Stage 3's narrow host bug fix may be scheduled beside diagnostics work if the file owner and resource slot remain available; large platform expansion follows alpha acceptance.
