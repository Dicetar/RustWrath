RustWrath — General Technical Handoff#

Project overview · architecture review · interaction diagnostics · seamless hotpatch roadmap

Purpose. Provide the owner and the next implementation agent with an actionable, evidence-labelled picture of RustWrath and a coherent direction for fixing gameplay failures while iterating in a live client. This is Handoff 1: General View. The detailed per-file implementation specification and coding-agent execution prompt are intentionally reserved for a later handoff.

01 — Project identity and immediate goal#

Repository: Dicetar/RustWrath · active branch: wotlk · inspected HEAD: 236b1a7aebc017655f9a0fc0dea54e52dae891ef (2026-11-02 UTC). The default main branch is a publication baseline and can lag the development branch. Begin every new session by checking the branch, HEAD, dirty working tree, and active owners; these coordinates will age.

RustWrath is a Rust/Bevy client targeting World of Warcraft: Wrath of the Lich King 3.3.5a, build 12340. It derives from the benilla Vanilla 1.12.1 client, while connecting to the owner's existing AzerothCore server and reading assets from the owner's game installation. The separate React/Vite/Three web preview is an independent artifact: web-preview success is not evidence of native-client gameplay. See README, CONTEXT, and AGENTS.

Near-term product promise: a private Windows alpha with login, realm and character navigation, entry into the world, and a real Northshire (Firna) quest → combat → loot → turn-in loop. Later platform ambitions include Souls-style combat, building, generated spaces, extensibility and the WorldMaster orchestration layer. A large collection of source files, unit tests and prototype subsystems already exists. Runtime acceptance of the entire route remains open in the cited project documents.

  • AzerothCore owns authoritative and durable world/player state. Client claims must reflect actually observed server state.
  • RustWrath client owns command intent, server-state projection, local prediction, graphical/UI presentation, diagnostics, and client-side patch activation.
  • WorldMaster (WM) is an existing Python orchestration service. Its native observation transport is a bounded loopback-only channel and is not a general untrusted patch-delivery service today. See benilla-wm-native.
  • The Vanilla donor and Wrath branch are separate compatibility targets. Retain 1.12 behavior behind explicit version boundaries and expand 12340 models where the semantics differ. The Wrath compatibility ADR was proposed at the inspected point; its approval should be revalidated.

Specific source concerns to carry forward#

  1. Outbound action admission: Wrath outbox code has a cap of 256 and logs a warning when full, while some calling sites ignore the return of send. The recorder should distinguish user intent, accepted into channel, accepted into outbox, actually written, and refused. Recording send() as success would hide real loss.
  2. Unbounded internal queues: Some crossbeam_channel::unbounded() session-event channels exist in the Wrath worker. Design bounded/backpressure semantics for high-rate telemetry, and separately review the correctness constraints for gameplay events; never silently discard critical ordered events.
  3. Count-handling parser risk: The item-stat reader clamps a declared statistic count with .min(64) instead of rejecting or consuming excess declared fields. On malformed packets, that can misalign subsequent parsing. Preserve as a targeted packet fuzz/regression case.
  4. Hotpatch failed-publication retry: In Host::poll, the manifest text is marked observed before TOML parsing / DLL opening completes. Re-reading the unchanged manifest then skips a candidate that previously failed transiently. Track attempted/succeeded/retryable states separately.
  5. UI diagnostic lifetime: DiagnosticLog is bounded (256 distinct messages) and owned by the UI model; a new VM clears it. The resident host should retain incidents through /reload and transitions, with explicit retention limits.
  6. CI gate semantics: .github/workflows/ci.yml gates same-repository PR jobs off via a head-repo check and has no push trigger. Confirm the repository's intended execution model, then establish evidence on the actual shared development branch.

03 — Revised solution: one observable transaction per meaningful player action#

Build three cooperating components:

  1. Interaction Flight Recorder (IFR) — persistent, structured, privacy-conscious telemetry. Captures user intent, UI callbacks, command admission, outbound serialization/writes, inbound decoded responses, reducer/state projections, Lua events and rendered/UI-visible consequences.
  2. Gameplay Contract Validator (GCV) — small, domain-specific finite-state machines that compare actual observations with expected outcomes. Categorizes successes, explicit server refusals, stalls, ambiguous matches and confirmed inconsistencies. Focus first on quests.
  3. Patch Revision Manager (PRM) — stages compatible module/content revisions, validates dependencies and ABI, activates at a safe boundary, observes health and reverts candidate client-side revisions if needed. It uses the same recorder and regression fixtures.

Keep them in the resident host. The stock Lua VM, addon scripts, UI frames and dynamically patched implementations may be rebuilt; the recorder's identity, pending incidents and patch history must persist through those lifecycles. A native recorder implementation requires one coordinated bootstrap build/restart to install its hooks. Future components can then use the stable interfaces it exposes.

Event chain and evidence levels#

<div class="sequence"><div><b>01</b><strong>Player intent</strong><span>Widget / key / world hit</span></div><div><b>02</b><strong>UI dispatch</strong><span>Event / Lua handler / guard</span></div><div><b>03</b><strong>Command admission</strong><span>Queue accepted or explicit refusal</span></div><div><b>04</b><strong>Socket writer</strong><span>Outbound packet written</span></div><div><b>05</b><strong>Server outcome</strong><span>Refusal / response / observed state</span></div><div><b>06</b><strong>Projection</strong><span>Reducer → ECS / quest store</span></div><div><b>07</b><strong>Presentation</strong><span>Lua event / journal / visible frame</span></div></div>

The strongest useful failure diagnosis is a specific boundary mismatch: “server-state transition observed; journal row absent,” “UI action admitted; writer refused,” or “Lua handler threw before creating a command.” An incomplete chain is reported as uncertain with the last confirmed stage. Generic timeouts alone rarely prove whether the server, client or UI is defective.

Correlation and limitations#

The stock 3.3.5 protocol provides no general client-generated interaction ID attached to every server reply. Generate a local interaction_id and correlate inbound events using (session_epoch, world_generation, quest_id, NPC GUID, command class, event sequence, monotonic time window). Track the candidate confidence as exact, strong, heuristic, or unmatched. Multiple simultaneous interactions and asynchronous background updates can cause ambiguity; preserve it.

A future negotiated WM-enhanced/server diagnostic channel could carry an explicit request ID for developer-only acknowledgments. Keep baseline 3.3.5 packets unchanged and preserve ordinary clients. Server instrumentation is optional and must honor AzerothCore authority; it should never invent gameplay confirmations.

06 — Broken UI diagnostics: logic, hit-testing and rendering#

A visible button can fail at several separate levels. Build a developer UI inspector with an always-resident event sink that records:

  • Input reachability: screen coordinates, logical pixel scale, target widget/frame identity, actual hit-test result, z-order, visibility, clipping/occlusion, active modal and mouse-capture owner.
  • Dispatch: OnMouseDown, OnClick, Lua callback invocation, exception, guard return, command emitted. Capture handler/file identity when available without logging arbitrary Lua source or secrets.
  • UI model: frame creation/teardown, loaded AddOn/FrameXML identity, missing methods/globals/CVars, event registration, QUEST_LOG_UPDATE/other event dispatch where applicable, expected data rows.
  • Layout/render: frame dimensions and coordinates, alpha/hidden states, draw-list presence, missing texture/font/shader, invalid geometry; optional screenshot/visual diff where a deterministic baseline exists.
  • Reload continuity: prior VM identity, requested reload, unload/save phase, fresh VM loaded, rebind succeeded, error count, player/world/session identity retained.

Use the existing script diagnostics, ui_script/lifecycle.rs, debug_panel, and the PowerShell diagnostics collector as integration points. The current overlay could gain a Recent Interactions tab and an Inspect Last Failed Click command.

UI success is an evidence ladder: handler invoked → model updated → widget bound/visible → pixels plausibly rendered. State and geometry checks can be automated consistently. Visual appearance, design quality and complex occlusion still benefit from manual inspection or carefully controlled screenshot baselines. Avoid claiming universal visual-bug detection.

07 — Diagnostic storage, reports and privacy#

Default behavior: in-memory rolling history of recent structured events, small summaries always on in developer builds, and selective detailed tracing per domain. Make the recorder bounded in event count, byte budget and disk age; use a non-blocking bounded writer with an explicit telemetry_events_dropped counter. Never block the render/input thread on diagnostic disk I/O. Consider tracing and a bounded logging/export sink; tracing-appender provides off-thread file writing primitives, but its queue/drop policy must be configured and tested for this use.

Illustrative defaults to benchmark, not mandated limits: a 60-second pre-incident circular window, 10,000 structured events in memory, a configurable 100 MiB local incident-storage budget, rotating JSONL files and a minimal user action to pin/export a case. Separate high-rate movement/animation sampling from loss-intolerant audit milestones. On overflow, preserve a trustworthy gap record so investigators know whether evidence is complete.

One-click bug report: the player presses a dev-key or chooses “Report last action.” The client captures an incident ID, chronological sanitized trace, summary/fingerprint, currently loaded patch/module/content versions, source + running executable digest, asset profile, recent bounded Lua errors, selected system snapshot and optionally a screenshot. It produces a local ZIP/JSONL/Markdown bundle. The user may add a short reproduction note. Automatic report preparation can coexist with manual initiation; automatic network upload should remain opt-in.

Redaction and minimization: exclude passwords, session/auth proofs, bearer tokens, channel passwords, private chat, remote player names, arbitrary packet bodies, database credentials, addon secrets, personal file paths and unapproved screenshots from shareable exports by default. The existing wire trace already handles some credential and chat cases, but a new exporter requires its own comprehensive allowlist and tests. Keep rich raw captures local and explicitly marked sensitive. Validate archive paths and prevent untrusted content from becoming executable on report import.

Report layout: summary.md, incident.json, events.jsonl, environment.json, active_revisions.json, ui_errors.json, protocol_summary.json, optional screenshot.png, optional replay_fixture.json. Every field should disclose observed vs inferred evidence and any data loss. Content provenance matters as much as Git revision.

08 — Hotpatch program: current reality and target design#

The objective is rapid iteration without losing the current player session whenever a supported patch class allows safe activation. ADR-0002 is the authoritative source for the current native pose path. The implemented sample has a DLL loader, a C ABI, immutable digest-named files and an atomic ready.toml publisher. The documentation reports a passing focused Bevy roundtrip test, while visible same-process in-game activation remains pending. The publish-pose-module.ps1 script is a real initial test vehicle.

Compatible WGSL source Opt-in embedded watching Hot-watch, compile, validate visible result; preserve previously working pipeline on failure
Lua/XML/addon UI VM reload lifecycle exists; content overlay work pending Versioned overlay + /reload with retained socket/character/world; explicit UI lifecycle checks

Stable host principle. Retain the Bevy ECS, GPU/device, socket, clocks, authoritative replicas, player identity, input and diagnostic services in the base executable. Dynamic modules implement explicit, versioned host interfaces and operate over borrowed bounded data at known schedule barriers. Avoid attempting to repeatedly install/uninstall arbitrary Bevy plugins, passing Rust-native structs/trait objects/allocators across unstable DLL boundaries, or running arbitrary untrusted DLLs inside the process.

Publication protocol, proposed v2:

  1. Build only the affected module or content unit; preserve the last-known-good runtime.
  2. Stage into a private candidate directory; attach source revision, runtime ABI/feature requirements, selected asset profile, dependency digests, full artifact hash (prefer SHA-256), and an authenticated publisher identity for remote delivery.
  3. Preflight schema, ABI, allowed paths, size, dependency closure, privacy/trust rules, deterministic offline regression cases and module-specific validation.
  4. Prepare resources and dependencies off the render-critical path where possible; existing assets and modules stay pinned. Await completion/error with bounded budgets and explicit states.
  5. Activate at a defined safe boundary. For the pose slice, validate a complete batch before promotion; for content, stage all dependent resources and commit the coherent revision as a unit.
  6. Observe health and functional invariants: frame time, panics/errors, GPU/asset failures, session epoch, world identity, quest state, inventory state and regression outcomes.
  7. Commit or revert. On candidate failure, restore the previous client-side revision and record the exact reason. Preserve the last-known-good artifacts and expose the active revision in diagnostics.
  8. Retire old resources safely after references/frames are released; enforce disk/memory retention and reject inconsistent or concurrent publishers.

The current sha1 digest is treated by ADR-0002 as local file identity/completeness, not authenticity. A remote WM publisher must use an authenticated/signature-capable delivery contract. A stronger digest such as SHA-256 is recommended for the new generalized manifest; migration should preserve backwards compatibility for the existing local ABI 1 loader.

Hotpatch incident and rollback rules#

  • Keep load failure, validation failure, activation failure, health regression, and manual rollback as distinct events. Preserve activation history and prior revision identity.
  • Fix the current loader's premature observed latch. Distinguish a broken permanent publication from a transient file lock/read failure; retry with capped backoff where appropriate. Never let a corrupted candidate thrash indefinitely.
  • Use single publisher / serialization for publication manifests; stage atomically, then activate after dependencies are ready. For WM delivery, authenticate origin, include replay protection/revision ordering and explicitly scope the target.
  • Treat native DLL crashes as process failures. Output validation cannot catch arbitrary memory corruption. Use only trusted local code and keep a crash-detectable last-known-good selection for safe next-launch recovery. True containment requires process isolation.
  • Client rollback restores client code/assets/state projections. It cannot undo irreversible server transactions such as quest hand-ins, gold transfers or combat outcomes. Never automatically replay such actions as validation.
  • “Seamless” requires measured budgets: no logout for compatible patches, no stale handle/collision changes, no visible duplicate animations/events, and bounded activation frame-time spikes. Report achieved measurements rather than asserting zero stutter.

First controlled hotpatch proof#

Use the existing local Windows development workflow, only after checking active build/client owners and confirming permission. Build the host with the hotpatch feature, launch the existing test character, then publish one pose module and its comparison implementation without restarting. The publisher supports -LiftDemo and -PassThrough; verify visually relevant output in the actual scene, the same PID, preserved session, revision switch, successful reversion and absence of transform accumulation. Then test a rejected candidate and a transient publishing failure. The benilla-hotpatch-bevy test is a useful bounded fixture; its Windows-native test is ignored by default and requires test artifacts.

Execution discipline: these are a planning catalog, not a command to run 20 live tests. The project currently limits authorized checks to at most 20 essential targeted cases per task, with the owner handling real login/combat and persistent changes. Most cases should be deterministic unit/headless fixtures. A small number of carefully approved live tests establish visible behavior. Record exact source/binary hashes, logs, test input and observed result for each executed case.

Definition of done for the first diagnostic slice#

A quest acceptance regression can be reproduced and attributed to one of: local input/handler, rejected command admission, outbound packet failure, explicit server refusal, unresolved server outcome, authoritative-state projection, or UI presentation. A single incident bundle must show the chain, IDs, timings, source/binary/patch identity, correlation confidence, missing evidence and applicable privacy scrubbing. At least one deliberately injected defect is detected, the normal path remains clean, and a live user scenario is recorded at the highest authorized evidence level.

Definition of done for first hotpatch slice#

Two different trusted pose implementations are activated in the same running PID, with a verified visual change and restored baseline. The active revision is shown; malformed and ABI-incompatible candidates leave the last-known-good pose in place. Performance and memory retention are measured. A simulated transient publication failure is recoverable. Call it pose-module hotpatch accepted, and keep content/native-gameplay/UI hotpatch acceptance separately tracked.

11 — Risk register and design decisions#

Priority Risk Response / trade-off
Critical In-process native patch crashes entire client Trusted publisher only; preflight; crash marker and next-start fallback; isolated process required for untrusted modules
High Correlation overclaims server acceptance Evidence ladder, confidence levels, server-authoritative state checks, optional negotiated diagnostic IDs
High Diagnostics mutate gameplay timing or memory use Fixed-cost fast path, bounded queues, sampling, overflow accounting and frame-time metrics
High Wrong Wrath/Vanilla semantic projection Keep version-specific contracts, tests against 12340/AzerothCore source and live known-good cases
High Live content swaps create mixed revisions Immutable graph-wide revision, dependency closure, prepare-before-commit, invalidation and rollback
High Hotpatch activation is a stall Prestage asynchronously; time the actual activation; budget and defer when unsafe
Medium Duplicate/missing Lua callbacks after reload Explicit VM teardown/rebuild contract, event-registration audit, repeated reload tests
Medium Reporter captures sensitive user material Allowlist export, local-only default, redaction tests, explicit screenshot/upload consent
Medium CI gives misleading green status Fix trigger coverage and capture run artifacts; do not substitute tests for visible gameplay
Medium Agent overlap invalidates evidence Single coordinator and Cargo/client slot; per-ticket ownership; checkout/binary identity proof

Decisions proposed for owner approval before large implementation: (A) permanent host-level diagnostics with low-cost always-on summaries; (B) manual activation for native DLL patches at first; (C) JSONL/ZIP local report format and default redaction; (D) one coherent content revision namespace shared by assets and UI; (E) server enhancements behind an explicit negotiated dev capability. They are proposed scope choices, not reported approvals.
